# Teddy v0.8 — local voice bootstrap, readiness and recovery

## Product contract

`./teddy.sh` starts the HTTP service immediately so the browser can show installation progress, then provisions the local speech stack when `TEDDY_PROVIDER=local`. HTTP liveness and Teddy availability are deliberately separate:

- `/api/health`: the local HTTP process is alive.
- `/api/availability`: installation phase, engine health, public artifact provenance/progress, restore availability and self-test result.
- `/api/ready`: HTTP 200 only after the complete managed ASR → LLM → TTS runtime has passed its canary; otherwise HTTP 503.

The talk control stays disabled until `/api/availability.ready` is true. A live Node server therefore cannot masquerade as a speaking Teddy.

## Managed public artifacts

The runtime manager discovers pinned public releases and requires SHA-256 metadata before promotion. Catalog and artifact transfers use bounded retry/backoff for transient network and upstream failures; first-install transient failures also receive bounded recovery cycles instead of becoming terminal process state. The UI publishes publisher, version, source, phase, transferred size and verified hash without exposing private local paths.

The first managed installation requires network access. Once a valid generation exists, normal local inference does not require an account or cloud provider. An optional `GITHUB_TOKEN` may be supplied to increase GitHub API rate limits, but it is not required by the product contract.

## Transactional generations and restore points

Runtime content is staged under `$TEDDY_HOME/runtime/staging/<id>`. Downloads are verified before extraction. A candidate is moved into `$TEDDY_HOME/runtime/generations/<id>`, engines are started, and the complete local self-test runs before the atomic `current.json` pointer changes. If candidate activation fails, Teddy attempts the prior `current.json` generation; the failed candidate never replaces the known-good pointer.

A managed generation is `pronto` only when all three engine health flags are true **and** the self-test is successful. The self-test exercises TTS → ASR → LLM → TTS with real local inference and validates non-empty transcription/reply plus valid WAV output.

Permanent integrity, layout and self-test failures fail closed. Public failure status identifies the failing stage, artifact/provider when applicable, HTTP status when present, and whether a retry is safe.

## Availability vocabulary

- `installazione`: discovery/download/verification/extraction/start/self-test is in progress.
- `pronto`: all engines plus managed self-test are healthy.
- `degradato`: a generation exists but the complete speech contract is not currently healthy.
- `non_disponibile`: there is no usable generation.

## Startup/recovery saturation

`npm run mutate:startup` evaluates exactly **1,000,000 deterministic mutation identities** across 20 operators. 900,000 are critical fault mutations and 100,000 are valid/benign controls. The critical operators cover missing engines, missing generation, failed self-test, invalid promotion/rollback choices, impossible byte progress, missing or insecure provenance/hash, degraded restore state, offline/no-generation state, installation-over-liveness, public-path leakage and false `ready` publication.

Expected report: `docs/startup-v8-report.json`; critical survivors = 0; unsafe = 0.

This is deterministic state/fault-space saturation, not one million physical model downloads or browser sessions. Real process and HTTP tests remain separate gates.
